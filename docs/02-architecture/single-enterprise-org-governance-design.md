# 单企业多部门治理设计

> 状态：已确认的 v1 设计
>
> 范围：单一企业部署、多个部门/团队、企业管理员统一治理。本文不设计多企业 SaaS，不引入 `tenant` 层，也不包含智能问数应用实现。

> **历史实施记录：** `docs/开发计划/CLOSED—单企业多部门治理闭环实施计划.md` 已完成并关闭。

## 1. 目标与非目标

### 目标

- 用现有 `org` 表示企业内部部门或团队。
- 企业管理员统一管理所有部门，部门管理员只管理本部门。
- 完成部门开通、用户分配、能力注册、Agent/Application 管理、配额和审计闭环。
- 保留当前 `org_id → JWT → RequestContext` 的可信隔离链路。
- 默认拒绝部门之间互相访问和共享；企业管理员可以显式向多个部门分发企业资源。

### 非目标

- 不增加 `tenant` / enterprise 数据层。当前部署只有一个企业。
- 不做公开自注册、邀请邮件、SSO、SCIM 的实现；只保留后续接入边界。
- 不做部门之间的自由共享、复杂 access-grant 图或多组织成员关系。
- 不定义聊天正文和文件正文的管理员访问权限；该能力留作后续决策。
- 不做计费系统、按 token 结算或 Skill Hub 市场。

### 当前实现与本设计的关系

当前代码已经具备部门级隔离底座：`users.org_id` 进入 JWT 和 `RequestContext`，核心用户/Agent/Application/Profile 查询按 org 过滤，`admin` / `org_admin` 路由边界和 entitlement 读写也已有实现与测试。现有组织页、用户页可以完成基础创建操作。

本设计补的是管理闭环：部门状态、原子开通、普通用户关闭自注册、首位/最后一名部门管理员保护、资源 `draft` 审核、企业资源分发、部门配额和治理审计。它不是对当前 Phase 7 的否定，而是把已完成的隔离底座推进为可运营的企业管理能力。

## 2. 权限模型

```text
admin       企业管理员：全企业治理与审计
org_admin   部门管理员：本部门治理
user        普通用户：使用已发布能力和 Agent
```

### 企业管理员（`admin`）

- 创建、改名、停用和归档部门。
- 创建、替换、停用部门管理员。
- 查看和管理全企业用户、Application、Agent、Profile、能力资源、配额和审计。
- 可以应急创建、重置或停用普通用户，但用户必须绑定明确的 `org_id`。
- 审核部门注册的资源，启用资源，或发布为企业级资源并分发给指定部门。
- 可以查看企业级运行状态、用量和治理信息。
- 聊天和文件内容访问暂不定义，不能从本设计推导出默认读取权。

### 部门管理员（`org_admin`）

- 只查看和管理自己的部门。
- 创建、重置和停用本部门普通用户。
- 创建和管理本部门 Application、Agent、Profile。
- 注册本部门 Skill、MCP、API、Plugin；资源默认私有且为 `draft`。
- 使用企业管理员已经发布到本部门的企业资源。
- 不能创建或授予 `admin` / `org_admin`。
- 不能跨部门读取、修改或共享资源。

### 普通用户（`user`）

- 必须由部门管理员创建；不允许公开自注册。
- 首次登录必须改密。
- 只能使用本部门已授权的 Application、Agent 和能力。

一个用户在 v1 只属于一个部门。企业管理员可以执行跨部门迁移；迁移后权限按新部门重新计算，历史数据迁移策略暂不定义。

## 3. 部门生命周期与开通

部门状态：

```text
provisioning → active → suspended → archived
```

- `provisioning`：开通尚未完成，不允许正常登录和使用。
- `active`：正常运行。
- `suspended`：禁止登录、新 AppKey/Widget token、WS 连接、Agent runtime 创建和恢复；数据保留，可由企业管理员恢复。
- `archived`：停止日常使用，仅允许企业管理员查询和导出治理数据；v1 不提供物理删除。

企业管理员通过“开通部门”流程完成：

1. 创建部门。
2. 创建首位 `org_admin`。
3. 设置首次改密状态。
4. 设置初始配额。
5. 选择或分发初始企业能力。
6. 写入开通审计。

开通应作为一个可回滚的服务端事务；失败不能留下可登录但未配置完成的半成品部门。

每个部门允许多个 `org_admin`，但不能停用最后一名有效部门管理员。停用部门时，应同时阻断该部门用户、AppKey、Widget、WS 和 runtime 的新使用。

## 4. 数据与隔离边界

现有 `org_id` 继续表示部门，不改名、不增加企业层：

```text
org
├── users
├── applications
├── agents
├── agent_profiles
├── registered_apis
├── capability entitlements
└── runtime / audit context
```

不变量：

- `org_id` 只能来自服务端可信身份源（`users.org_id` → JWT claim → `RequestContext`），不能来自请求 body、query 或可伪造的路径参数。
- 所有部门资源读写必须经过 `RequestContext` 和 ownership 检查。
- AppKey 的组织必须与用户 JWT 的组织一致。
- 企业管理员可以跨 org 管理，但普通查询仍需明确记录目标 org。
- 部门管理员跨 org 访问统一表现为拒绝或“未找到”，避免泄漏资源存在性。
- 部门之间默认不共享聊天、文件、Agent、Application 或私有能力资源。

## 5. 能力资源管理

资源分两种可见范围：

```text
org-private       部门私有
enterprise        企业管理员发布的企业资源
```

部门管理员和企业管理员都可以注册资源，但注册权限不等于执行权限：

```text
注册 → draft → 企业管理员审核 → active → 分发/使用
```

- 部门管理员注册的 Skill/MCP/API/Plugin 默认属于本部门、状态为 `draft`。
- 企业管理员创建的企业资源可以直接启用；部门管理员创建的资源必须经过企业管理员审核。
- 企业管理员可以审核部门资源、禁用资源、发布为企业资源，并分发给多个部门。
- 部门管理员不能将资源发布给其他部门。
- 禁用资源后，新的 capability resolve 必须立即排除；已有 runtime 按现有停止/重建策略失效。
- 最终能力仍按交集计算：资源有效性 ∩ 部门 entitlement ∩ Application allowlist ∩ Agent activation。
- 平台治理守卫（deny-default、路径校验、MCP 前缀、审计）不能被任何管理员或应用覆盖。

## 6. Application 与 Agent

v1 中 Application 和 Agent 默认属于单个部门，不做部门间自由共享。

- 部门管理员创建和维护本部门 Application、Agent、Profile。
- 企业管理员可以查看和管理全部部门对象。
- 企业管理员需要向多个部门提供同一能力时，采用“企业管理员分发/配置”动作，而不是允许部门之间互相授权。
- 不复制平台实例；平台实例内可存在多个部门和多个应用。
- 应用层的业务语义、业务数据库和专属前端不属于本治理设计范围。

## 7. 配额与审计

企业管理员按部门配置最小治理配额：

```text
maxAgents
maxConcurrentRuntimes
maxStorageMb
maxTurnsPerRuntime
```

v1 不实现计费和 token 结算。创建 Agent、启动 runtime、上传文件和执行受限操作前做服务端配额校验，超限返回明确错误并写审计。

治理审计默认保留 180 天，企业管理员可查看和导出。记录：

- 操作者、角色、部门、时间和 request/trace id。
- 对象类型、对象 id、原 org、新 org。
- 创建、修改、启用、禁用、分发、撤销、迁移等动作。
- 成功/失败和失败原因摘要。
- 配置版本或 capability drift 信息。

默认不记录密码、token、secret、聊天正文、文件正文或外部 API payload。

## 8. 管理界面闭环

现有“组织”和“用户”页面是底座，目标补成以下企业管理入口：

```text
企业总览
├── 部门管理
│   ├── 开通部门
│   ├── 状态/停用/归档
│   └── 部门详情
├── 用户管理
│   ├── 创建/重置/停用
│   ├── 部门分配/迁移
│   └── 部门管理员管理
├── 应用与 Agent
├── 能力资源
│   ├── draft 审核
│   ├── 部门私有资源
│   └── 企业资源分发
├── 配额与用量
└── 审计与导出
```

部门管理员只看到本部门视图；企业管理员看到企业视图。聊天和文件内容查看入口暂不实现，也不在 UI 中暗示已有该能力。

## 9. 实施顺序

按依赖顺序拆成可独立验证的闭环：

1. **部门开通闭环**：部门状态、开通事务、首位管理员、初始配额。
2. **用户生命周期闭环**：关闭自注册、创建/重置/停用、部门迁移、JWT 失效策略。
3. **管理员闭环**：多部门管理员、最后管理员保护、企业总览和部门详情。
4. **资源治理闭环**：私有资源、draft 审核、企业发布、部门分发、禁用失效。
5. **配额审计闭环**：服务端配额守卫、用量摘要、180 天治理审计和导出。

每个闭环完成后执行：

```bash
npx tsc --noEmit
npm run test:skill-config
npm run build
```

并补充跨部门越权、停用部门、最后管理员、资源 draft/active/disabled 和配额超限测试。

## 9. 用户级 MEMORY.md（一用户一文档）

每个认证用户拥有且仅拥有一份 `MEMORY.md`，由该用户的所有 Agent / Chat 共享读写；不建用户级 `CLAUDE.md`、不建向量库或记忆正文表、不跨用户/跨部门共享。

- 边界与本文治理一致：记忆以 `userId`（orgId 作为配额/可见性边界）隔离；Agent 只能挂载当前认证用户的记忆。
- 平台是不变量来源（`systemPrompt` / control plane），用户记忆只是一份受控文档，不参与 capability 决策。
- 企业 admin 可读正文、配置配额、清空重建（审计仅记录元数据，不存正文）；不提供记忆开/关开关。
- 自动 Write/Edit 仅对当前用户那份确切的 `MEMORY.md` 放行（配额内），其它路径（`CLAUDE.md`、`/workspace/input`、他人记忆等）沿用既有审批/拒绝策略。

## 10. 明确后置项

- 邮件邀请和真实邮件发送。
- SSO/OIDC/SAML/SCIM。
- 多组织成员和组织切换。
- 聊天正文、文件正文的企业管理员访问策略。
- 计费、套餐和 token 成本归集。
- 多企业 tenant 层和独立企业部署。
- Skill Hub 市场与外部包交付。

本文是单企业、多部门治理的 v1 设计；若未来转为多企业 SaaS，应另立架构专项，不在本设计上直接叠加隐含层级。
