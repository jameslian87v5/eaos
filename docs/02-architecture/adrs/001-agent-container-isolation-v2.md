# ADR-001: Agent容器化隔离架构决策 v2.0 (最终版)

## 状态

**状态**: ✅ 已批准 (Approved)  
**日期**: 2024-06-06  
**决策者**: Claude Code + User + Codex Collaboration  
**版本**: v2.0 (基于Codex反馈更新)

## 背景

当前Simple ChatApp项目存在严重的安全风险：

1. **危险工具权限**: Agent有Bash、Write、Edit等危险工具权限
2. **无隔离**: Agent运行在主服务器进程中，无隔离保护
3. **资源无限制**: Agent可以无限制消耗服务器资源
4. **数据安全**: 企业数据可能被Agent访问或泄露

### 问题陈述

如何为企业内部AI助手设计安全、可控的Agent运行环境，实现：
- 用户间Agent完全隔离
- 资源使用可控
- 企业数据安全
- 部署和运维简单

## 决策

采用**L2容器沙盒隔离 + Agent Runtime Manager动态管理**方案，每个活跃会话一个独立的Docker容器运行Agent。

### 核心架构

```
Web API → Agent Runtime Manager → Docker API → 动态Agent容器 → Egress Proxy → 外部HTTPS
```

### 技术选型

| 维度 | 选择 | 理由 |
|------|------|------|
| **隔离等级** | L2 容器沙盒 | 平衡安全性和性能，适合企业内部环境 |
| **容器引擎** | Docker (rootless) | 成熟稳定，企业IT团队熟悉 |
| **管理方式** | Agent Runtime Manager + Docker API | Compose管理基础设施，动态容器由Manager创建 |
| **网络控制** | 独立Egress Proxy | 防止SSRF，控制出站访问 |
| **部署模式** | 按需创建 + 小型热池 (2-3容器) | 平衡响应速度和资源效率 |
| **容量模型** | 10-100注册用户，3-20并发 | 符合企业内部实际使用情况 |

### 架构对比

#### v1.0方案 vs v2.0方案

| 方面 | v1.0 (初步方案) | v2.0 (最终方案) |
|------|----------------|----------------|
| **容器管理** | Docker Compose管理所有容器 | Agent Runtime Manager调用Docker API |
| **隔离粒度** | 每个用户一个容器 | 每个活跃会话一个容器 |
| **容量模型** | 10-100用户同时运行 | 10-100注册用户，3-20并发 |
| **网络控制** | 简单域名白名单 | 独立Egress Proxy + internal网络 |
| **工具权限** | 统一L2隔离 | L1/L2/L2+/L3分级 |
| **安全机制** | 5层防护 | 12层防护 |
| **实施计划** | 5-7周 | 8周 |

### 核心特性

1. **会话隔离**: 每个活跃会话/任务一个隔离容器，用户级目录与权限绑定
2. **资源限制**: CPU 1核，内存 1GB，磁盘 2GB，进程数100
3. **文件系统隔离**: 用户独立工作目录，只读根文件系统
4. **网络隔离**: Egress Proxy + internal网络，只允许HTTPS出站
5. **工具权限分级**: L1/L2/L2+/L3分级系统
6. **审计日志**: 完整的工具使用和操作日志

## 替代方案

### 方案A: 进程内隔离 (L1)

**描述**: Agent继续运行在主服务器进程中，只限制工具权限

**优点**:
- 部署最简单
- 无冷启动延迟
- 资源效率最高

**缺点**:
- 隔离最弱，安全性差
- 单个Agent可能影响整个服务器
- 资源无限制

**结论**: ❌ 不采用，隔离不足

### 方案B: 单容器多任务 (Dify模式)

**描述**: 所有Agent运行在单个容器中，通过进程级隔离

**优点**:
- 部署简单
- 无冷启动延迟
- 资源效率高

**缺点**:
- 容器内进程间隔离弱
- 单个Agent失控可能影响其他Agent
- 安全性不如容器级隔离

**结论**: ❌ 不采用，隔离不足

### 方案C: K8s Pod级隔离 (LangGraph模式)

**描述**: 每个Agent运行在独立的K8s Pod中

**优点**:
- 隔离性强
- K8s原生管理
- 水平扩展性好

**缺点**:
- 部署复杂度高
- 需要专业运维
- 对10-100用户规模过度设计

**结论**: ❌ 当前不采用，预留升级路径

### 方案D: microVM隔离 (L3)

**描述**: 使用Firecracker或gVisor实现内核级隔离

**优点**:
- 隔离性极强
- 接近VM的安全性

**缺点**:
- 冷启动慢（3-10秒）
- 资源消耗大
- 部署复杂

**结论**: ❌ 当前不采用，高风险场景可考虑

## Codex反馈与采纳

### Codex关键建议

1. **✅ 容量模型调整**: 采用10-100注册用户，3-20并发活跃Agent
2. **✅ 容器管理架构**: 使用Agent Runtime Manager调用Docker API
3. **✅ 安全机制增强**: 加入rootless、userns-remap、非root、cap_drop等
4. **✅ 工具权限分级**: 实现L1/L2/L2+/L3分级系统
5. **✅ 实施计划调整**: 8周计划，加入威胁分析和安全测试
6. **✅ 风险补充**: 补充单点故障、数据残留、日志泄露等风险点

### 安全机制增强（基于Codex建议）

**新增安全层**:
1. Rootless Docker / User Namespace
2. 非Root用户
3. Capabilities控制 (CapDrop: ALL)
4. No-New-Privileges
5. 只读根文件系统
6. 进程数限制 (PidsLimit)
7. 资源限制 (CPU/Memory/OOM)
8. Seccomp系统调用白名单
9. 网络隔离 (internal网络)
10. Egress Proxy (Squid/Envoy)
11. DNS控制
12. 工具权限分级与审计

## 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 单点故障 | 高 | 考虑双机部署或迁移到K8s |
| 数据残留 | 中 | 容器彻底清理或只复用干净镜像 |
| 日志泄露 | 高 | 不保存敏感数据，脱敏处理 |
| SSRF攻击 | 高 | Egress Proxy + 内网阻断 |
| 资源耗尽 | 中 | 配额控制 + 队列化 |
| 容器逃逸 | 低 | 多层防护 + 及时更新 |
| 供应链攻击 | 中 | 镜像固定digest + 扫描 |
| 长期凭证泄露 | 高 | 使用短期token + 最小权限 |
